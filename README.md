# DevOpsDeployWebServer
[![Live
Demo](https://img.shields.io/badge/Live%20Demo-195.140.147.132-blue)](http://195.140.147.132)
[![Repository](https://img.shields.io/badge/GitHub-Repository-black?logo=github)](https://github.com/Rogotochka/DevOpsDeployWebServer)

**Учебный DevOps-проект:** контейнеризация PHP-приложения,
автоматическая сборка образов и доставка релиза на VPS с помощью GitHub
Actions и Ansible.

-   **Демо:** http://195.140.147.132
-   **Исходный код:**
    https://github.com/Rogotochka/DevOpsDeployWebServer

> Проект предназначен для демонстрации практических навыков DevOps. Демо
> доступно по HTTP; HTTPS в текущей конфигурации не заявлен.

## Что реализовано

-   **Docker и Docker Compose** --- приложение разделено на веб-сервер,
    PHP-FPM и PostgreSQL.
-   **Nginx** --- принимает HTTP-запросы, отдаёт публичные файлы и
    передаёт PHP-запросы в PHP-FPM через FastCGI.
-   **PHP-FPM** --- запускает PHP-приложение в отдельном контейнере на
    базе официального `php:8.4-fpm-alpine`; образ устанавливает
    расширения для работы с PostgreSQL.
-   **PostgreSQL 17** --- отдельный контейнер для хранения данных;
    данные вынесены в именованный volume `postgres_data`, чтобы
    пересоздание контейнера не удаляло базу.
-   **GitHub Container Registry (GHCR)** --- хранение собранных
    Docker-образов, которые сервер получает при развёртывании.
-   **GitHub Actions** --- автоматизация CI/CD для сборки и публикации
    образов.
-   **Ansible** --- автоматизация подготовки Debian VPS и выкладки
    приложения: установка Docker, подготовка каталога, авторизация в
    GHCR, установка Compose-конфигурации, загрузка образов и запуск
    сервисов.
-   **Проверка после деплоя** --- Ansible ожидает HTTP-ответ `200` от
    `/api/health`; если проверка не проходит, задача развёртывания
    завершается ошибкой.

## Архитектура

``` text
Разработчик
    |
    | git push
    v
GitHub Repository
    |
    v
GitHub Actions
    | build Docker images
    | push images
    v
GitHub Container Registry (GHCR)
    ^
    | docker-compose pull
    |
Ansible ── SSH ──> Debian VPS
                       |
                       v
                 Docker Compose
                       |
          +------------+------------+
          |            |            |
          v            v            v
       Nginx         PHP-FPM     PostgreSQL
       :80            :9000       :5432
          |            |            |
          | FastCGI    |            +--> postgres_data volume
          +----------->|
```

Внешний HTTP-порт опубликован у Nginx. PHP-FPM и PostgreSQL работают как
отдельные сервисы Compose; PHP доступен Nginx во внутренней сети Docker,
а PostgreSQL --- PHP в сети backend. Для сети `backend` задан параметр
`internal: true`, поэтому она предназначена для внутреннего
взаимодействия контейнеров, а не для прямого внешнего доступа.

## Как проходит развёртывание

1.  Изменения отправляются в GitHub.
2.  GitHub Actions собирает Docker-образы приложения и публикует их в
    GHCR.
3.  Ansible подключается к Debian VPS и обеспечивает наличие Docker и
    Compose.
4.  Ansible создаёт рабочий каталог `/opt/php-prod-deploy`, копирует
    `compose.yaml` и генерирует `.env`.
5.  Сервер авторизуется в GHCR и получает версии образов, указанные
    переменной `IMAGE_VERSION`.
6.  `docker-compose up -d` запускает или обновляет сервисы.
7.  Ansible проверяет `http://127.0.0.1/api/health`.
8.  После загрузки образов Ansible выполняет выход из GHCR.

## Ключевые инженерные задачи и решения

### 1. Повторяемый деплой вместо ручного обновления сервера

**Проблема:** ручное копирование файлов и запуск контейнеров на сервере
легко приводит к расхождению конфигураций и ошибкам при обновлениях.

**Решение:** описать шаги развёртывания в Ansible, а состав приложения
--- в `compose.yaml`. Это делает процесс воспроизводимым и сокращает
количество ручных действий.

### 2. Разделение приложения на сервисы

**Проблема:** веб-сервер, обработчик PHP и база данных имеют разные роли
и требования к запуску.

**Решение:** вынести Nginx, PHP-FPM и PostgreSQL в отдельные контейнеры.
Nginx передаёт PHP-запросы сервису `backend:9000`, а PHP подключается к
базе по имени сервиса `database:5432`. Compose обеспечивает сетевое
взаимодействие через DNS имён сервисов.

### 3. Защита секретов при развёртывании

**Проблема:** пароли базы данных и токены реестра нельзя хранить в
открытом виде в репозитории или выводить в CI/CD-логах.

**Решение в проекте:** 
- учётные данные передаются Ansible из переменных окружения CI/CD; 
- токен GHCR передаётся в `docker login` через стандартный ввод (`--password-stdin`);
- -задача авторизации GHCR использует `no_log: true`, чтобы скрывать её вывод;
- Ansible создаёт серверный `.env` с правами `0600` и владельцем `root`; - после загрузки
образов выполняется `docker logout ghcr.io`.

Секреты для запуска pipeline должны храниться в GitHub Actions Secrets,
а не в YAML-файлах репозитория. Токен для скачивания образов следует
ограничивать необходимыми правами, например `read:packages`.

### 4. Ограничение сетевого доступа между компонентами

**Проблема:** PHP-FPM и PostgreSQL не должны публиковать свои служебные
порты напрямую в Интернет для работы сайта.

**Решение:** в Compose наружу опубликован порт Nginx `80:80`. PHP-FPM и
PostgreSQL не имеют опубликованных портов; взаимодействие между ними
организовано через внутренние сети Docker. Сеть `backend` объявлена с
`internal: true`.

Это уменьшает поверхность атаки, хотя само по себе не заменяет настройку
межсетевого экрана VPS и контроль доступа на уровне хоста.

### 5. Снижение утечки информации через Nginx

В конфигурации Nginx отключён вывод версии сервера
(`server_tokens off`), ограничен максимальный размер тела запроса
(`client_max_body_size 2m`) и запрещён доступ к скрытым файлам, кроме
пути `.well-known`. Это снижает избыточное раскрытие информации и
ограничивает размер принимаемых запросов.

### 6. Сохранность данных при обновлении контейнеров

**Проблема:** данные базы не должны исчезать при пересоздании контейнера
PostgreSQL.

**Решение:** данные PostgreSQL хранятся в именованном Docker volume
`postgres_data`, а не только в файловой системе контейнера. Обычное
обновление образа не требует удаления этого тома.

> Docker volume не заменяет резервное копирование. Для production-среды
> отдельно необходимы проверенные бэкапы и процедура восстановления.

### 7. Проверка результата, а не только факта запуска

**Проблема:** успешный запуск контейнеров ещё не означает, что
приложение отвечает на запросы.

**Решение:** после обновления Ansible проверяет endpoint `/api/health`,
ожидая HTTP `200` с повторными попытками. Это позволяет обнаруживать
часть проблем сразу в процессе деплоя.

## Стек технологий

  Область                        Технологии
  ------------------------------ -------------------------------------------------
  ОС сервера                     Debian VPS
  Контейнеризация                Docker, Docker Compose
  Web                            Nginx
  Backend                        PHP 8.4, PHP-FPM
  База данных                    PostgreSQL 17
  CI/CD                          GitHub Actions
  Реестр образов                 GitHub Container Registry
  Автоматизация инфраструктуры   Ansible
  Сеть контейнеров               Docker bridge networks, внутренняя сеть backend
  Хранение данных                Docker named volume

## Структура репозитория

``` text
.
├── .github/
│   └── workflows/       # GitHub Actions workflows
├── ansible/
│   ├── deploy.yml       # автоматизация развёртывания
│   └── templates/       # шаблоны конфигурации, включая app.env.j2
├── app/
│   ├── public/          # публичная часть PHP-приложения
│   └── src/             # исходный код приложения
├── docker/
│   ├── nginx/           # конфигурация Nginx
│   └── php/             # Dockerfile PHP-FPM
└── compose.yaml         # сервисы, сети и volume
```

## Что демонстрирует проект

-   построение контейнерной архитектуры веб-приложения;
-   создание Docker-образов и публикацию в реестре контейнеров;
-   автоматизацию CI/CD и доставки релизов;
-   применение Ansible для конфигурации сервера и развёртывания;
-   передачу секретов через CI/CD без включения их в исходный код;
-   сегментацию контейнерных сетей и минимизацию опубликованных портов;
-   сохранение состояния базы данных при обновлении приложения;
-   проверку доступности приложения после релиза.

## Возможные дальнейшие улучшения

Следующие пункты стоит рассматривать как направления развития, а не как
уже реализованные функции:

-   настроить HTTPS с автоматическим продлением TLS-сертификата;

-   добавить автоматические тесты и проверки безопасности образов в CI;
-   организовать резервное копирование PostgreSQL и тест восстановления;
-   добавить мониторинг, централизованные логи и уведомления о неудачных
    деплоях;

## Запуск и конфигурация

Для развёртывания необходимы доступ к GHCR. 
Параметры окружения приложения и базы данных задаются через
переменные окружения и шаблон `ansible/templates/app.env.j2`.
Чувствительные значения не следует коммитить в Git.

Конкретный перечень GitHub Actions Secrets должен соответствовать
workflow в `.github/workflows/`. В процессе деплоя используются учётные
данные GHCR, передаваемыи Ansible из окружения.
